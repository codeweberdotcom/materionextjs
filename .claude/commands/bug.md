# Исправление бага

Исследуй и исправь баг, следуя строгому workflow: АНАЛИЗ → ПЛАН → ОДОБРЕНИЕ → РЕАЛИЗАЦИЯ → ТЕСТИРОВАНИЕ → ОТЧЁТ.

> **Полный процесс работы с документацией:** см. [docs/AI_WORKFLOW_GUIDE.md](../../docs/AI_WORKFLOW_GUIDE.md)

## Использование

- `/bug <описание проблемы>` — e.g., `/bug чат показывает skeleton после rate limit`
- `/bug` — спросить описание у пользователя

## Аргумент: $ARGUMENTS

## ВАЖНО: Правила работы

- **НИКОГДА** не вноси изменения без явного одобрения пользователя
- **НИКОГДА** не удаляй данные (Redis, DB, файлы) без спроса
- **НИКОГДА** не перезапускай сервисы без спроса
- Сначала АНАЛИЗ, потом ПЛАН, потом ЖДИ одобрения
- Каждый шаг — отдельное сообщение пользователю

## Шаги

### 1. АНАЛИЗ (только чтение, без изменений!)

**Цель:** понять root cause. Разрешено только читать, искать, логи.

Действия:
- Воспроизвести или понять сценарий бага из описания
- Найти релевантные файлы (`Grep`, `Glob`, `Read`)
- Проверить логи если нужно:
  ```bash
  # Логи приложения
  ls -la logs/
  # Логи Docker
  docker logs --tail 50 materio-<service>
  # Redis состояние
  docker exec materio-redis redis-cli KEYS "*pattern*"
  # БД состояние
  docker exec materio-postgresql psql -U postgres -d materio -c "SELECT ..."
  ```
- Проверить git blame/log для изменённых файлов
- Изучить связанные сервисы, middleware, hooks

**Результат анализа — сообщение пользователю:**

```
## 🔍 Анализ бага: <краткое название>

**Симптом:** <что видит пользователь>

**Root cause:** <почему это происходит>

**Затронутые файлы:**
- `path/to/file.ts:123` — описание
- `path/to/file2.ts:45` — описание

**Связанные модули:** <какие сервисы/компоненты затронуты>

**Серьёзность:** Critical / High / Medium / Low
```

### 2. ПЛАН (предложить варианты, НЕ реализовывать!)

**Цель:** предложить варианты решения с trade-offs.

**Результат — сообщение пользователю:**

```
## 📋 План исправления

**Вариант A:** <описание>
- ✅ Плюсы: ...
- ⚠️ Минусы: ...
- Файлы: ...

**Вариант B:** <описание>
- ✅ Плюсы: ...
- ⚠️ Минусы: ...
- Файлы: ...

**Рекомендация:** Вариант X, потому что ...

**Побочные эффекты:** <что может сломаться>

**Нужно ли менять данные (Redis/DB)?** Да/Нет — <что именно>
```

### 3. ОДОБРЕНИЕ

**⏸️ СТОП. Жди ответа пользователя.**

Не продолжай пока пользователь не скажет:
- Какой вариант выбрать
- Или предложит свой
- Или попросит доработать план

### 4. РЕАЛИЗАЦИЯ (только после одобрения!)

Действия:
- Внести изменения в код согласно одобренному плану
- Если план требует изменения данных (Redis, DB) — выполнить
- Минимальные изменения — не рефакторить код вокруг бага
- Не добавлять "улучшения" которые не были в плане

### 5. ТЕСТИРОВАНИЕ

Действия:
- Запустить линтер на изменённых файлах: `pnpm lint`
- Запустить связанные тесты если есть:
  ```bash
  pnpm vitest run tests/unit/path/to/related-test.ts
  pnpm vitest run tests/integration/path/to/related-test.ts
  ```
- Проверить что баг исправлен (если возможно автоматически)
- Проверить что ничего не сломалось (smoke test)

### 6. ОТЧЁТ

**Результат — сообщение пользователю:**

```
## ✅ Баг исправлен: <краткое название>

**Что было:** <описание проблемы>

**Причина:** <root cause>

**Что сделано:**
- `path/to/file.ts` — описание изменения
- `path/to/file2.ts` — описание изменения

**Тесты:** ✅ lint passed, ✅ unit tests passed

**Как проверить:** <шаги для пользователя>

**Сохранить в документацию?** Да/Нет
```

После отчёта **спроси пользователя**: «Сохранить анализ и решение в документацию проекта?»

- Если **да** — следуй шаблонам из [docs/AI_WORKFLOW_GUIDE.md](../../docs/AI_WORKFLOW_GUIDE.md):
  - Анализ → `docs/analysis/[категория]/analysis-[модуль]-[описание]-[дата].md`
  - План → `docs/plans/active/plan-[модуль]-[описание]-[дата].md`
  - Отчёт → `docs/reports/[тип]/report-[модуль]-[описание]-[дата].md`
  - Обновить `docs/STATUS_INDEX.md`
- Если **нет** — достаточно коммита с описанием

Пользователь сам решает, глобальная это проблема или нет. Не навязывай сохранение.

## Классификация серьёзности

| Уровень | Описание | Примеры |
|---------|----------|---------|
| **Critical** | Приложение не работает, потеря данных | Сервер падает, авторизация сломана, данные удаляются |
| **High** | Основной функционал сломан | Чат не загружается, пользователи не создаются, загрузка файлов падает |
| **Medium** | Функционал работает некорректно | Неправильные данные, сломан UI элемент, ошибки валидации |
| **Low** | Косметические проблемы | Опечатки, неправильные иконки, мелкие UI баги |

## Типичные места для поиска

| Симптом | Где искать |
|---------|-----------|
| API возвращает ошибку | `src/app/api/`, `src/lib/api/withApiHandler.ts`, логи |
| Страница не загружается | `src/app/[lang]/...`, middleware.ts, auth checks |
| Чат не работает | `src/hooks/useChatNew.ts`, `src/lib/sockets/`, Redis rate limits |
| Rate limit блокирует | Redis keys `materio:ratelimit:*`, `src/lib/rate-limit/` |
| Permissions не работают | `src/utils/permissions/`, `src/hooks/usePermissions.ts`, role в DB |
| Перевод отсутствует | `src/data/dictionaries/*.json`, ключ в navigation |
| Стили сломаны | `src/@core/theme/`, Tailwind classes, MUI overrides |
| Загрузка файлов | `src/services/media/`, S3 config, queue status |
| WebSocket не подключается | `src/server/websocket-standalone.ts`, порт 3001, CORS |

## Запреты

- НИКОГДА не удаляй данные из Redis/DB без одобрения
- НИКОГДА не перезапускай сервисы без одобрения
- НИКОГДА не меняй код до этапа РЕАЛИЗАЦИЯ
- НИКОГДА не пропускай этап ПЛАН и ОДОБРЕНИЕ
- НЕ рефакторь код вокруг бага — только минимальный фикс
- НЕ добавляй "заодно" улучшения, которых нет в плане
