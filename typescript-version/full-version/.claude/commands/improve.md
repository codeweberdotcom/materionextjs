# /improve — Доработка существующего функционала

## Описание
Команда для улучшения, расширения или оптимизации существующего функционала. Не для исправления багов (используй `/bug`).

> **Полный процесс работы с документацией:** см. [docs/AI_WORKFLOW_GUIDE.md](../../docs/AI_WORKFLOW_GUIDE.md)

## Workflow

### 1. АНАЛИЗ
- Изучить текущую реализацию функционала
- Найти **аналогичный функционал** в проекте и изучить его паттерны
- Понять как данные хранятся, как передаются, как отображаются
- Проверить какие модули/компоненты затронуты
- Изучить документацию в `docs/` если есть

**Вопросы для анализа:**
- Как это работает сейчас?
- Как аналогичная задача уже решена в других модулях?
- Какие паттерны используются (API, компоненты, хуки, сервисы)?
- Какие файлы будут затронуты?

### 2. ПЛАН
Представить пользователю:
- Что именно меняется
- Список файлов для изменения
- Какие паттерны проекта будут использованы (с примерами откуда взяты)
- Побочные эффекты и обратная совместимость
- Что НЕ будет затронуто

### 3. ОДОБРЕНИЕ
**СТОП. Ждать явного одобрения пользователя.**
- НЕ начинать реализацию без одобрения
- НЕ вносить "небольшие правки" попутно
- Если пользователь просит изменить план — обновить и снова ждать одобрения

### 4. РЕАЛИЗАЦИЯ
- Следовать **существующим паттернам проекта** — не изобретать новые подходы
- Если в проекте есть аналог — копировать его подход
- Единообразие важнее "лучшего" решения
- Использовать TodoWrite для отслеживания прогресса

**Правила:**
- Именование параметров, переменных, ключей — как в аналогичных местах проекта
- API формат ответов — через `apiResponse.*` или `NextResponse.json()` как в соседних routes
- Компоненты — те же хуки, контексты, паттерны что в соседних модулях
- Переводы — через существующую систему i18n (JSON-словари + БД + `getDictionary`/`useTranslation`)
- Валидация — Zod как везде в проекте

### 5. ПРОВЕРКА
- Проверить что функционал работает (API, UI)
- `pnpm lint` — без ошибок
- Проверить обратную совместимость — старый функционал не сломан

### 6. ОТЧЁТ
Краткий отчёт:
- Что было → что стало
- Какие файлы изменены
- Что проверено

### 7. ДОКУМЕНТАЦИЯ

Спросить пользователя: **"Сохранить в документацию?"**

- Если **да** — следуй шаблонам из [docs/AI_WORKFLOW_GUIDE.md](../../docs/AI_WORKFLOW_GUIDE.md):
  - Анализ → `docs/analysis/[категория]/analysis-[модуль]-[описание]-[дата].md`
  - План → `docs/plans/active/plan-[модуль]-[описание]-[дата].md`
  - Отчёт → `docs/reports/[тип]/report-[модуль]-[описание]-[дата].md`
  - Обновить `docs/STATUS_INDEX.md`
- Если **нет** → завершить

## Ключевые принципы

### Единообразие > Креативность
Перед реализацией ОБЯЗАТЕЛЬНО найти аналог в проекте:
- Новый API route → посмотреть как сделаны соседние routes
- Новый перевод → посмотреть как переводятся другие модули
- Новый компонент → посмотреть как устроены соседние компоненты
- Новый сервис → посмотреть паттерны в `src/services/`

### Не ломать существующее
- Обратная совместимость — запросы без новых параметров работают как раньше
- Не менять сигнатуры существующих функций без необходимости
- Не удалять поля/параметры которые могут использоваться

### Масштабируемость
- Решение должно легко расширяться (новые языки, новые сущности, новые модули)
- Не хардкодить — использовать конфигурацию и данные из БД/словарей

## Типичные места для изучения

| Задача | Где смотреть аналог |
|--------|-------------------|
| API route | Соседние routes в `src/app/api/` |
| Перевод данных | `/api/menu/route.ts` — `getDictionary(locale)` |
| UI-лейблы | `useTranslation()` + `dictionary.*` в компонентах |
| Права доступа | `usePermissions()`, `withApiHandler` с permission |
| Таблица данных | Соседние `*ListTable.tsx` в `src/views/` |
| Валидация | `src/lib/validations/` и `src/schemas/` |
| Сервис | `src/services/` — singleton с `getInstance()` |
| Redux state | `src/redux-store/slices/` |
