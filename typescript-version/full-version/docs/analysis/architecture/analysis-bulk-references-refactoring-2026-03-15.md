# Анализ модуля массовых операций справочников

**Дата проведения:** 2026-03-15
**Статус:** Завершен
**Приоритет:** Высокий

---

## Цель анализа

Оценка архитектуры, типизации, оптимизации и расширяемости модуля bulk-операций для справочников (Countries, States, Cities, Districts).

---

## Текущее состояние

### Что анализируется:

- `src/app/api/admin/references/_bulk-handler.ts` — shared handler для bulk routes
- `src/services/bulk/configs/referenceBulkConfig.ts` — 12 конфигов для 4 сущностей x 3 операции
- `src/services/bulk/BulkOperationsService.ts` — глобальный singleton-сервис
- `src/services/bulk/types.ts` — типы и интерфейсы
- `src/lib/validations/reference-schemas.ts` — Zod-схема валидации
- 12 route-файлов `src/app/api/admin/references/*/bulk/*/route.ts`
- 4 таблицы `src/views/apps/references/*/\*ListTable.tsx`

### Методология:

- Ревью кода всех слоёв модуля
- Сравнение с аналогами (`userBulkConfig`, `UserListTable`, `withApiHandler`)
- Анализ типизации, дублирования, расширяемости

---

## Результаты анализа

### Найденные проблемы:

#### Архитектура

1. **`_bulk-handler.ts` дублирует `withApiHandler`**
   - Описание: Handler вручную реализует auth (`requireAuth`), permission check (`checkPermission`), user lookup (`prisma.user.findUnique`), error handling — всё это стандартно делает `withApiHandler` в остальных routes проекта
   - Влияние: Высокое — нарушает конвенции проекта, не подключает rate-limiting и HTTP-метрики
   - Приоритет: Высокий

2. **`referenceBulkConfig.ts` — 280 строк копипасты**
   - Описание: 12 конфигов отличаются только `modelName`, `permissionModule` и Prisma-моделью. Логика `getRecords`, `updateOperation`, `deleteOperation` идентична для всех сущностей
   - Влияние: Среднее — при добавлении нового справочника нужно писать +90 строк одинакового кода
   - Приоритет: Высокий

3. **12 route-файлов boilerplate**
   - Описание: Каждый route-файл — 2 строки логики. Можно заменить динамическим route `[entity]/bulk/[action]/route.ts`
   - Влияние: Среднее — при добавлении нового действия (bulk/assign) нужно создать ещё 4 файла
   - Приоритет: Средний

4. **Мёртвый `import { prisma }` в `referenceBulkConfig.ts`**
   - Описание: Импорт не используется — операции принимают `tx: TransactionClient`
   - Влияние: Низкое
   - Приоритет: Низкий

#### Типизация

5. **Generic `<T>` в конфигах не используется**
   - Описание: Все конфиги типизированы как `BulkOperationConfig` без generic. `getRecords` возвращает `{ id: true }` — generic бесполезен
   - Влияние: Низкое
   - Приоритет: Средний

6. **`environment` — несоответствие типов**
   - Описание: В `_bulk-handler.ts` кастится к `'production' | 'test' | undefined`, но в `BulkOperationsService` принимает `string`
   - Влияние: Низкое
   - Приоритет: Низкий

#### Оптимизация

7. **`refetchData()` — полная перезагрузка после bulk-операции**
   - Описание: После каждой bulk-операции 4 таблицы делают полный refetch всех данных с сервера. При 10K городов это тяжёлый запрос
   - Влияние: Высокое — UX деградация при больших объёмах данных
   - Приоритет: Высокий

8. **`getRecords` — мёртвый код**
   - Описание: `BulkOperationsService.bulkUpdateWithContext` и `bulkDeleteWithContext` нигде не вызывают `config.getRecords`. Конфиги объявляют его, но он не используется
   - Влияние: Среднее — лишний код в конфигах
   - Приоритет: Средний

9. **Повторный `prisma.user.findUnique` в handler**
   - Описание: `_bulk-handler.ts` делает отдельный запрос для получения user с ролью, хотя `withApiHandler` уже это делает
   - Влияние: Среднее — лишний DB-запрос на каждый bulk request
   - Приоритет: Средний

#### Расширяемость

10. **UI bulk-логика дублируется в 4 таблицах**
    - Описание: ~80 строк идентичной логики (state, handlers, loading, refetch) в каждой из 4 таблиц. Отличие только в URL endpoint и refetch URL
    - Влияние: Высокое — при изменении логики (добавление bulk/assign) нужно менять 4 файла
    - Приоритет: Высокий

11. **Нет поддержки `bulk/assign`**
    - Описание: Массовое присвоение полей (страна, область, тип) невозможно. `BulkOperationsService` поддерживает `data: Record<string, unknown>`, но в handler и конфигах `data` всегда `{}`
    - Влияние: Среднее — ограничивает функциональность
    - Приоритет: Средний

12. **Нет rate-limiting на bulk эндпоинтах**
    - Описание: В отличие от других admin endpoints, bulk routes не используют rate-limiting
    - Влияние: Среднее — потенциальный abuse
    - Приоритет: Средний

### Найденные возможности:

1. **Фабричная функция** — `createReferenceBulkConfigs()` сократит 280 строк до ~40
2. **Хук `useReferenceBulkOperations`** — вынесет общую UI-логику, подготовит к bulk/assign
3. **Динамический route** — 1 файл вместо 12, расширяемость без создания файлов
4. **Оптимистичное обновление** — улучшит UX при больших объёмах данных

## Рекомендации

1. **Перевод на `withApiHandler`** — привести `_bulk-handler.ts` к стандарту проекта
   - Оценка сложности: Средняя
   - Файлы: `_bulk-handler.ts` + 12 route-файлов

2. **Фабрика конфигов** — заменить 12 конфигов функцией-генератором
   - Оценка сложности: Низкая
   - Файлы: `referenceBulkConfig.ts`

3. **Хук `useReferenceBulkOperations`** — вынести общую логику из 4 таблиц
   - Оценка сложности: Средняя
   - Файлы: новый хук + 4 таблицы

4. **Динамический route** — заменить 12 route-файлов одним
   - Оценка сложности: Средняя
   - Файлы: 1 новый + удаление 12

---

## Выводы

Модуль функционален и корректно работает. Основные проблемы — дублирование кода и несоответствие конвенциям проекта (`withApiHandler`). Рефакторинг сократит объём кода в ~4 раза и значительно упростит добавление новых справочников и операций (bulk/assign).
