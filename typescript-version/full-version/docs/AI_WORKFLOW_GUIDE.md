## 📖 Разница между документами

- **QUICK_START.md** - краткий справочник для людей (где что хранить, как найти информацию)

## 🎯 Общий процесс работы

При получении задачи на внедрение новой функции или доработку, AI должен следовать следующему процессу:

```
1. АНАЛИЗ → 2. ПЛАН → 3. РЕАЛИЗАЦИЯ → 4. ТЕСТИРОВАНИЕ → 5. ОТЧЕТ → 6. ДОКУМЕНТАЦИЯ
```

## 🧪 Шаг 4 - ТЕСТИРОВАНИЕ

### Когда проводить тестирование:

- ✅ После завершения реализации или этапа реализации
- ✅ Перед созданием отчета
- ✅ При исправлении багов
- ✅ Перед развертыванием

### Где создавать отчеты по тестированию:

```
docs/reports/testing/report-[модуль]-[дата].md
```

### Типы тестирования:

#### 1. Unit тесты

**Когда использовать:**

- Тестирование отдельных функций/компонентов
- Проверка бизнес-логики
- Валидация входных/выходных данных

**Где размещать:**

- В проекте: рядом с тестируемым кодом или в папке `__tests__/`
- Пример: `src/components/Button/__tests__/Button.test.tsx`

**Что тестировать:**

- Отдельные функции
- Компоненты в изоляции
- Утилиты и хелперы
- Редьюсеры и селекторы

**Критерии качества:**

- Покрытие кода: минимум 80%
- Все граничные случаи покрыты
- Тесты независимы и изолированы

---

#### 2. Integration тесты

**Когда использовать:**

- Тестирование взаимодействия между компонентами
- Проверка работы API endpoints
- Тестирование интеграции с внешними сервисами

**Где размещать:**

- В проекте: `tests/integration/` или `__tests__/integration/`

**Что тестировать:**

- Взаимодействие компонентов
- API endpoints
- Интеграция с базой данных
- Интеграция с внешними сервисами

**Критерии качества:**

- Все основные сценарии покрыты
- Тесты стабильны и воспроизводимы
- Используются моки для внешних зависимостей

---

#### 3. E2E (End-to-End) тесты

**Когда использовать:**

- Тестирование полных пользовательских сценариев
- Проверка критических путей приложения
- Перед релизом

**Где размещать:**

- В проекте: `tests/e2e/` или `cypress/e2e/` (если используется Cypress)

**Что тестировать:**

- Критические пользовательские сценарии
- Полные workflows
- Интеграция всех слоев приложения

**Критерии качества:**

- Все критические пути покрыты
- Тесты стабильны
- Быстрое выполнение (оптимизация при необходимости)

---

#### 4. Ручное тестирование

**Когда использовать:**

- Проверка UI/UX
- Валидация визуальных аспектов
- Тестирование на разных устройствах/браузерах

**Чек-лист ручного тестирования:**

- [ ] Проверка на разных браузерах (Chrome, Firefox, Safari, Edge)
- [ ] Проверка на разных устройствах (Desktop, Tablet, Mobile)
- [ ] Проверка доступности (a11y)
- [ ] Проверка производительности
- [ ] Проверка визуального дизайна
- [ ] Проверка обработки ошибок
- [ ] Проверка валидации форм

---

**Дата проведения:** YYYY-MM-DD  
**Версия:** X.Y.Z  
**Тестировщик:** [Имя/ID]

## ⚠️ Важные правила

1. **Всегда создавать документы в правильных папках:**
- Анализы → `docs/analysis/[категория]/`
- Планы → `docs/plans/active/` или `docs/plans/roadmap/`
- Отчеты → `docs/reports/[тип]/`
- ТЗ → `docs/requirements/active/`

2. **Всегда обновлять индексы:**
- `STATUS_INDEX.md` - при создании/изменении статуса
- `README.md` - при добавлении новой документации

3. **Всегда использовать правильные имена файлов:**
- Формат: `[тип]-[модуль]-[описание]-[дата].md`
- Пример: `analysis-export-data-requirements-2025-01-23.md`

4. **Всегда связывать документы:**
- План → Анализ/ТЗ
- Отчет → План
- Документация → Отчет

5. **Всегда обновлять статусы:**
- При завершении → переместить в `completed/`
- При отмене → переместить в `archived/` или отметить как отменен
