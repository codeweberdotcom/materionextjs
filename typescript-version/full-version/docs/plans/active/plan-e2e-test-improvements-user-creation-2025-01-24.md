## ⚠️ Риски и митигация

1. **Изменение существующих метрик может сломать дашборды**
   - Описание: Добавление нового label `environment` может изменить существующие запросы PromQL
   - Вероятность: Средняя
   - Влияние: Высокое
   - Митигация:
     - Использовать значение по умолчанию `environment="production"` для существующих запросов
     - Обновить все дашборды после добавления label
     - Протестировать на staging окружении

2. **Производительность при большом количестве тестов**
   - Описание: Создание/удаление пользователей для каждого теста может замедлить выполнение
   - Вероятность: Средняя
   - Влияние: Среднее
   - Митигация:
     - Использовать параллельное выполнение тестов с изоляцией
     - Оптимизировать API endpoints для быстрого создания/удаления
     - Рассмотреть возможность переиспользования пользователей для группы тестов

3. **Смешивание тестовых и реальных данных**
   - Описание: Если различение не работает корректно, тестовые данные могут попасть в продакшн метрики
   - Вероятность: Низкая
   - Влияние: Критическое
   - Митигация:
     - Тщательное тестирование механизма различения
     - Использование нескольких механизмов одновременно (label + metadata + префикс)
     - Мониторинг метрик на наличие аномалий

4. **Несовместимость с существующими тестами**
   - Описание: Существующие тесты могут использовать статические пользователи
   - Вероятность: Высокая
   - Влияние: Среднее
   - Митигация:
     - Постепенная миграция тестов
     - Сохранение обратной совместимости где возможно
     - Обновление всех тестов в рамках одного этапа

5. **SQL запросы с NULL значениями**
   - Описание: Старые события без `metadata.environment` могут быть неправильно отфильтрованы
   - Вероятность: Средняя
   - Влияние: Высокое
   - Митигация:
     - Использовать правильные SQL запросы с `IS NULL` проверкой
     - Тестировать фильтрацию на данных со старыми событиями
     - По умолчанию считать отсутствие environment как production

## 📝 Примечания

### Стратегия очистки данных

- **Удалять после теста:**
  - Пользователи и связанные данные (профили, настройки)
  - Rate limit состояния (Redis ключи)
  - Блокировки (manual blocks)
  - In-memory кеши

- **НЕ удалять (сохранять для аналитики):**
  - События (events) - помечены `metadata.environment="test"`
  - Метрики Prometheus - помечены `environment="test"`
  - Логи - помечены соответствующими тегами

### Механизмы различения

1. **Метрики Prometheus:** label `environment` ("test" | "production")
2. **События:** `metadata.environment`, `metadata.testRunId`, `metadata.testSuite`
3. **Пользователи:** email с префиксом `test+` или доменом `@test.example.com`
4. **Rate limits:** префикс `test:` в ключах
5. **Заголовки:** `x-test-request: true`, `x-test-run-id`, `x-test-suite: e2e`

### Примеры фильтрации

**PromQL (исключить тесты):**

```promql
rate_limit_checks_total{environment="production"}
rate_limit_checks_total{environment!="test"}
```

**SQL (исключить тесты, с учетом NULL):**

```sql
-- Вариант 1: Явная проверка NULL
SELECT * FROM events
WHERE (
  metadata->>'environment' IS NULL
  OR metadata->>'environment' != 'test'
)

-- Вариант 2: COALESCE (считать отсутствие как production)
SELECT * FROM events
WHERE COALESCE(metadata->>'environment', 'production') != 'test'
```

**Redis (только тесты):**

```redis
KEYS test:*
```

### Retention Policy

- **Тестовые события:** удаляются через 30 дней (настраивается через `EVENT_RETENTION_TEST_EVENTS_DAYS`)
- **Реальные события:** удаляются согласно политике для каждого источника (обычно 90 дней)
- **Автоматическая очистка:** выполняется через `EventRetentionService.cleanTestEvents()`

### Переменные окружения

```bash
# Retention policy для тестовых событий (дни)
EVENT_RETENTION_TEST_EVENTS_DAYS=30
```
